# Database Schema — recipes-manager

Authoritative Postgres schema. Implementation lives in `src/server/dal/schema.sql`
and is applied idempotently at backend startup.

This document is the source of truth for table shapes, constraints, and indexes.
Any DDL change must update this file in the same commit as the SQL change.

---

## 1. Conventions

- **Database**: PostgreSQL ≥ 14.
- **Naming**: `snake_case` for all table and column names.
- **IDs**: every entity surrogate key is `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
  Junction tables have no surrogate id (composite primary keys instead), per the
  system spec.
- **Timestamps**: `TIMESTAMPTZ` (UTC). Default `now()`. Never `TIMESTAMP` (no tz).
- **Strings**: `TEXT` everywhere (no `VARCHAR(n)`). Length bounds are enforced
  in the application layer (FastAPI / Pydantic) for clearer error messages.
- **Numbers**: amounts are `DOUBLE PRECISION`. We do not need decimal precision
  for nutrition data and shopping list quantities.
- **Boolean defaults**: explicit. No reliance on Postgres defaults for nullable
  flags.
- **Foreign keys**: always declared, with explicit `ON DELETE` behavior.

---

## 2. Required extension

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

`pg_trgm` powers similarity-based name search (`recipes`, `products`). It must
be created before the GIST indexes that reference `gist_trgm_ops`.

The Postgres container ships with `pg_trgm` available; the backend simply
issues `CREATE EXTENSION IF NOT EXISTS pg_trgm;` at startup.

---

## 3. Enum type

```sql
DO $$ BEGIN
  CREATE TYPE quantity_type AS ENUM ('weight', 'volume');
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;
```

`CREATE TYPE` does not support `IF NOT EXISTS`, hence the `DO` block. Allowed
values are exactly `'weight'` (per 100 g) and `'volume'` (per 100 ml).

Adding a new enum value later requires `ALTER TYPE quantity_type ADD VALUE`,
which is non-transactional. This is acceptable: v1 has only the two values and
they are unlikely to grow.

## 4. Tables

### 4.1 `users`

```sql
CREATE TABLE IF NOT EXISTS users (
  id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  username    TEXT        NOT NULL UNIQUE,
  full_name   TEXT,
  pwd_hash    TEXT        NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

| Column | Type | Notes |
|---|---|---|
| `id` | BIGINT | PK, identity. |
| `username` | TEXT | Unique, NOT NULL. Application enforces 3-50 chars and `^[a-zA-Z0-9_.-]+$`. |
| `full_name` | TEXT | Nullable. Up to 200 chars (app-level). |
| `pwd_hash` | TEXT | bcrypt hash; cost factor 12. NOT NULL. |
| `created_at` | TIMESTAMPTZ | Defaults to `now()`. |

Indexes: PK + unique on `username` are sufficient.

### 4.2 `nutrition_fact_types`

```sql
CREATE TABLE IF NOT EXISTS nutrition_fact_types (
  id    BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name  TEXT NOT NULL UNIQUE,
  unit  TEXT NOT NULL
);
```

Static reference data. Seeded on startup (see §6). Five rows in v1: Energy,
Protein, Net Carbs, Fat, Fibers.

`ON DELETE` from this table is `RESTRICT` everywhere it is referenced — these
rows are never deleted.

### 4.3 `products`

```sql
CREATE TABLE IF NOT EXISTS products (
  id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name                TEXT        NOT NULL,
  image_filename      TEXT,
  created_by_user_id  BIGINT      REFERENCES users(id) ON DELETE RESTRICT,
  import_source       TEXT,
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT products_origin_xor CHECK (
    (created_by_user_id IS NULL) <> (import_source IS NULL)
  )
);
```

- The CHECK enforces "exactly one of `created_by_user_id` or `import_source`".
- `ON DELETE RESTRICT` on `created_by_user_id` prevents user deletion if any of
  their products still exist (user deletion is not an API operation in v1, but
  the constraint protects against accidental cleanup).
- `name` is not unique — multiple users may legitimately have a product called
  "Apple".
- `image_filename` is the UUID4-named filename on the shared volume; nullable.

### 4.4 `product_nutrition_facts`

```sql
CREATE TABLE IF NOT EXISTS product_nutrition_facts (
  product_id          BIGINT          NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  nutrition_fact_id   BIGINT          NOT NULL REFERENCES nutrition_fact_types(id) ON DELETE RESTRICT,
  quantity_type       quantity_type   NOT NULL,
  amount              DOUBLE PRECISION NOT NULL CHECK (amount >= 0),
  PRIMARY KEY (product_id, nutrition_fact_id, quantity_type)
);
```

- No surrogate id (system spec).
- Composite PK enforces "no duplicate `(nutrition_fact_id, quantity_type)` per product".
- `ON DELETE CASCADE` from `products` cleans up facts on product delete.
- `amount` constrained to non-negative.

### 4.5 `recipes`

```sql
CREATE TABLE IF NOT EXISTS recipes (
  id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name                TEXT        NOT NULL,
  description         TEXT,
  image_filename      TEXT,
  created_by_user_id  BIGINT      REFERENCES users(id) ON DELETE RESTRICT,
  import_source       TEXT,
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT recipes_origin_xor CHECK (
    (created_by_user_id IS NULL) <> (import_source IS NULL)
  )
);
```

Same shape and rationale as `products`, plus optional `description`.

### 4.6 `recipe_products`

```sql
CREATE TABLE IF NOT EXISTS recipe_products (
  recipe_id      BIGINT          NOT NULL REFERENCES recipes(id) ON DELETE CASCADE,
  product_id     BIGINT          NOT NULL REFERENCES products(id) ON DELETE RESTRICT,
  quantity_type  quantity_type   NOT NULL,
  amount         DOUBLE PRECISION NOT NULL CHECK (amount > 0),
  PRIMARY KEY (recipe_id, product_id)
);
```

- Composite PK: same product can appear at most once per recipe (matches the
  decision locked in the planning artifact).
- `ON DELETE CASCADE` from `recipes` cleans up entries when a recipe is deleted.
- `ON DELETE RESTRICT` from `products` prevents deleting a product that any
  recipe still references; the API surfaces this as `409 Conflict`.
- `quantity_type` is a regular column (not part of PK).
- `amount > 0` enforced at the DB layer.

#### Application-layer invariant

`recipe_products.quantity_type` must match an existing
`product_nutrition_facts(product_id, quantity_type)` row. This is **not**
expressible as a single FK because `product_nutrition_facts`'s PK is
`(product_id, nutrition_fact_id, quantity_type)` and we don't constrain on a
specific `nutrition_fact_id`. The check is enforced in the service layer on
recipe create/update, and re-verified by phase-5 integration tests.

### 4.7 `recipe_stars`

```sql
CREATE TABLE IF NOT EXISTS recipe_stars (
  user_id     BIGINT      NOT NULL REFERENCES users(id)   ON DELETE CASCADE,
  recipe_id   BIGINT      NOT NULL REFERENCES recipes(id) ON DELETE CASCADE,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, recipe_id)
);
```

Per-user starring of recipes. `created_at` records when the star was placed —
used as the sort key for the "Starred Recipes" listing (most-recently-starred
first).

`ON DELETE CASCADE` both directions: deleting a user removes their stars;
deleting a recipe removes all stars on it.

### 4.8 `product_stars`

```sql
CREATE TABLE IF NOT EXISTS product_stars (
  user_id     BIGINT      NOT NULL REFERENCES users(id)    ON DELETE CASCADE,
  product_id  BIGINT      NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, product_id)
);
```

Symmetric to `recipe_stars`.

## 5. Indexes

Beyond the indexes implied by primary keys and unique constraints, the
following indexes are required:

### 5.1 Trigram GIST indexes for name search

```sql
CREATE INDEX IF NOT EXISTS recipes_name_trgm_idx
  ON recipes USING GIST (name gist_trgm_ops);

CREATE INDEX IF NOT EXISTS products_name_trgm_idx
  ON products USING GIST (name gist_trgm_ops);
```

These power the `scope=search` listing on recipes and products. Search uses
`similarity(name, $1) >= $threshold` plus `ORDER BY similarity(name, $1) DESC`.
The threshold defaults to `0.3` and is read from env `SEARCH_SIMILARITY_THRESHOLD`.

### 5.2 Foreign-key support indexes

Postgres does **not** auto-index FK columns. The following are required for
common query paths:

```sql
CREATE INDEX IF NOT EXISTS recipes_created_by_user_id_idx
  ON recipes(created_by_user_id);

CREATE INDEX IF NOT EXISTS products_created_by_user_id_idx
  ON products(created_by_user_id);

CREATE INDEX IF NOT EXISTS recipe_products_product_id_idx
  ON recipe_products(product_id);
```

`recipe_products_product_id_idx` is essential for the "is this product still
referenced by a recipe?" check on `DELETE /api/products/{id}` and for any
future shopping-list query that joins by product.

The `recipe_stars` and `product_stars` PK already covers `(user_id, *_id)`, so
the leftmost-prefix `(user_id)` predicate is satisfied without an additional
index.

### 5.3 Pagination support indexes

For chronological list pagination on `scope=mine`:

```sql
CREATE INDEX IF NOT EXISTS recipes_created_at_id_desc_idx
  ON recipes(created_at DESC, id DESC);

CREATE INDEX IF NOT EXISTS products_created_at_id_desc_idx
  ON products(created_at DESC, id DESC);
```

These also accelerate `scope=mine` filtering since the planner can combine the
sorted scan with a `WHERE created_by_user_id = $1` filter; for the dataset
sizes envisioned in v1 the post-filter cost is negligible.

For `scope=starred` pagination ordered by when the user starred each item:

```sql
CREATE INDEX IF NOT EXISTS recipe_stars_user_created_at_idx
  ON recipe_stars(user_id, created_at DESC, recipe_id DESC);

CREATE INDEX IF NOT EXISTS product_stars_user_created_at_idx
  ON product_stars(user_id, created_at DESC, product_id DESC);
```

## 6. Seed data

`nutrition_fact_types` is the only table with seeded rows. Seeding is
idempotent (safe to run on every startup):

```sql
INSERT INTO nutrition_fact_types (name, unit) VALUES
  ('Energy',    'kcal'),
  ('Protein',   'g'),
  ('Net Carbs', 'g'),
  ('Fat',       'g'),
  ('Fibers',    'g')
ON CONFLICT (name) DO NOTHING;
```

The order of the rows (and therefore their assigned ids in a fresh database) is
not part of the contract: queries reference rows by `name` or by id returned
from `GET /api/nutrition-fact-types`, never by hardcoded ids.

## 7. Schema initialization

The backend has no migration tool. On startup the entrypoint runs an
idempotent initialization step:

1. Open a connection to Postgres using `POSTGRES_*` env vars.
2. Read the contents of `src/server/dal/schema.sql` (a single file containing
   everything in §2 + §3 + §4 + §5 + §6, in that order).
3. Execute the file in a single transaction.
4. Log success and continue startup.

All DDL statements use `IF NOT EXISTS` (or `DO` blocks for `CREATE TYPE`) so
the file is safe to re-run on every boot. There is no version table; the
single source of truth for the schema is the SQL file in the repo.

If the backend is ever started against a database with an older schema (from a
previous code version), the safest course in v1 is to drop and recreate the
database. Schema-evolution support is out of scope.

## 8. Cross-cutting behaviors

### 8.1 Cascading

| Source row deleted | Effect |
|---|---|
| `users` row | `RESTRICT` from `products`, `recipes`. CASCADE from `recipe_stars`, `product_stars`. (User deletion is not an API operation in v1.) |
| `products` row | CASCADE → `product_nutrition_facts`, `product_stars`. RESTRICT from `recipe_products` (delete blocked by 409 if referenced). |
| `recipes` row | CASCADE → `recipe_products`, `recipe_stars`. |
| `nutrition_fact_types` row | RESTRICT from `product_nutrition_facts` (these rows are never deleted in v1). |

### 8.2 Image files

Image files on the shared volume are not tracked in any table beyond the
`image_filename` column. Deleting an entity does not delete its image file —
copies may share the filename, and orphan cleanup is out-of-scope for v1.

### 8.3 Concurrency

All mutating endpoints run inside a single transaction per HTTP request. The
backend uses SQLAlchemy Core with `asyncpg`. Read-only endpoints use
auto-commit.

There is no row-level locking pattern beyond what the constraints provide.
Concurrent stars or recipe updates are resolved by the unique/PK constraints
(idempotent re-stars) or by last-write-wins (recipe edits — single user owns
each recipe so contention is not expected).

### 8.4 Time

`created_at` is set by Postgres `now()` at insert time. The application does
not pass `created_at` from the client. Returned values use ISO 8601 with `Z`
offset.
